可观测、可审批、可回放的 Agent 运行时样板

这里不演示“AI 很聪明”。它要回答的是另一类问题： Agent 跑完之后，你说得清它做了什么、凭什么做、挂了怎么复现吗？ 下面四格就是答案的存放位置，每一格数据都能点开看它从哪来。

挂了能续吗？检查点 + resume + 事件导出，进程重启也不丢证据。
数据从哪来？数据集有版本和切分，实验参数可对比，不编造指标。

从这里开始

这个项目要解决的问题是：Agent 跑完后说不清它做了什么、凭什么做、出了问题怎么复现。 走完下面三步，你就能亲手看到这三件事分别被记在哪。

三步看懂这个项目

  1. 发起一次运行——在「发起一次运行」里写一句话任务，点执行。你会拿到一个 run_id，这是这次运行唯一的身份。
  2. 检查这次运行——在「检查运行」里按 run_id 查：计划（planner 拆成了哪些任务）、事件流（每一步发生了什么）、 trace（父子 span 与耗时）、summary（成功率和 token）。四项对不上，说明埋点漏了。
  3. 看边界——在「工具与技能」里看每个工具的 permission。读工具直接跑；需要确认的会挂起等 approval， 这就是“Agent 不能自作主张”的落点。

当前 planner 版本是 deterministic/1：它把任务拆成一个 execute 节点，不调用大模型。 这是刻意留的最小可验证骨架——先把可观测和可审批做扎实，再替换 planner。 同理，多模态实验在没有 GPU 时会直接标 unavailable，而不是编一个好看的指标。

发起一次运行

写一句话描述你的任务。系统会立刻生成 plan，并返回 run_id。执行是可选的第二步——先看 plan 再决定跑不跑。

运行已创建切到「检查运行」继续

检查运行

plan 回答“打算怎么做”，events 回答“实际做了什么”， trace 回答“花了多久”，summary 回答“结果算好还是坏”。

run_id 显示在「发起一次运行」的结果里；创建时会自动填到这里。
